# BZOGAK 성능 구조

## 목표

카메라, OCR, 책장, 인사이트 기능을 유지하면서 탭 전환과 긴 글조각 목록의 응답성을 안정적으로 유지한다. 성능 변경은 화면 결과보다 작업 시점과 렌더링 범위를 줄이는 데 집중한다.

## 적용한 원칙

### 안정적인 탭 수명주기

- 최상위 화면은 커스텀 영구 탭 컨테이너 안에서 처음 방문할 때 한 번 생성하고 탭 이동 때 다시 만들지 않는다.
- 캡처, 책장, 인사이트의 탐색 스택과 로컬 상태를 탭 이동 후에도 유지한다.
- 시스템 `TabView`와 별도 하단 메뉴를 함께 사용하지 않아 시스템 탭바가 중복 표시될 가능성을 제거한다.
- 방문하지 않은 탭은 만들지 않아 첫 화면 시작 비용을 늘리지 않는다.

### 하나의 카메라 세션

- 앱 루트에서 `CameraTextScanner` 하나를 소유하고 캡처 화면에 전달한다.
- `AVCaptureSession`과 카메라 코어는 화면의 `body` 계산 중 만들지 않고, 앱 루트가 표시된 뒤 메인 액터 밖에서 준비한다.
- 캡처 탭 진입 시 제스처가 진행 중이지 않으면 메인 액터의 추가 작업을 거치지 않고 즉시 시작 큐로 전달한다.
- 같은 시작 요청이 겹치면 이미 실행 중인 세션에서 병합하고, 이탈 후 짧은 유예 시간 뒤 정지한다.
- 사용자가 바로 돌아오면 예정된 정지를 취소해 세션 재구성 비용을 피한다.
- 밑줄긋기와 읽어주기가 같은 세션을 넘겨받는 동안 이전 화면의 지연 중지 작업이 새 화면의 카메라를 끄지 않도록 소유권을 구분한다.
- 두 촬영 화면은 하나의 `AVCaptureSession`과 하나의 `AVCaptureVideoPreviewLayer`를 공유한다. 탭 전환은 레이어를 화면 호스트 사이에서 이동시키며 세션을 재시작하지 않는다.
- 카메라 전환 문제는 `CameraLifecycle` 로그의 화면 소유자, 요청 번호, 세션 큐 대기, 실행 완료, 미리보기 연결, 첫 프레임 순서로 진단한다.
- OCR/Vision 분석은 기존처럼 제스처 완료 뒤에만 활성화한다.
- 카메라 세션 큐는 사용자 인터랙션에 맞는 우선순위를 사용한다.
- iOS 26 이상에서는 미리보기 레이어는 즉시 시작하고, OCR용 비디오 출력만 지연 시작 대상으로 유지한다.

### 비동기 저장

- UI 상태 변경 직후 만드는 전체 라이브러리 스냅샷의 JSON 인코딩과 SwiftData 저장을 메인 액터 밖에서 실행한다.
- 저장 세대 번호를 사용해 오래된 비동기 작업이 최신 저장 상태를 덮어쓰지 못하게 한다.
- 앱이 비활성화될 때 진행 중인 저장을 완료한다.
- 읽어주기 진입에서는 화면과 카메라를 먼저 표시하고, 임시 글 파일 확인과 저장 본문의 문장 분리는 비동기로 수행한다.

### 조회 인덱스와 파생 상태

- 책 ID와 글조각 ID 조회는 매번 전체 배열을 찾지 않고 갱신 시 만든 인덱스를 사용한다.
- 최근 글조각과 전체 글조각 수는 변경 시 한 번 계산한다.
- 같은 화면 패스에서 검색 결과와 선택 수를 여러 번 필터링하지 않고 지역 값으로 재사용한다.
- 모든 데이터 변경을 루트 화면에 전달하던 광범위한 revision 관찰을 제거했다. 재생 중인 글조각 삭제처럼 필요한 사건만 알림으로 전달한다.

### 가벼운 렌더링

- 전체 화면마다 반복하던 배경을 앱 루트 한 곳에서만 그린다.
- 화면 크기 전체를 매번 순회하던 `Canvas` 질감은 작은 정적 타일 이미지로 교체했다.
- 글조각 카드의 실시간 전체 blur, saturation, shadow 조합을 제거하고 정적 투명 표면으로 단순화했다.

## 다음 측정 항목

실제 성능 수치는 데이터가 충분히 쌓인 실제 아이폰의 Release 빌드에서 Instruments로 측정한다.

1. 앱 첫 실행과 재실행의 Time Profiler 비교
2. 캡처에서 책장/인사이트로 이동할 때 메인 스레드 점유 시간
3. 긴 글조각 목록 스크롤 중 SwiftUI body 업데이트와 GPU 프레임 시간
4. 카메라 시작, 중지, 재진입 구간의 세션 구성 시간
5. 대규모 라이브러리의 초기 SwiftData 로드 및 JSON 복원 시간

초기 라이브러리 복원은 현재 동기식이다. 실제 대규모 데이터에서 콜드 스타트 병목으로 확인될 때만 단계적 hydration으로 변경한다. App Intents와 공유 상태가 같은 라이브러리를 사용하므로 측정 없이 비동기 초기화로 바꾸지 않는다.

## Xcode 디버거 첫 실행 주의

Xcode 26.6에서 실제 iPhone에 새 빌드를 설치한 직후 `Debug executable`이 켜져 있으면, 앱 코드와 무관한 디버거 준비 구간 때문에 첫 화면이 약 24~28초 멈춘 것처럼 보일 수 있다. 같은 빌드에서 `Debug executable`을 끄거나, Xcode 실행을 정지한 뒤 기기에서 앱을 직접 다시 열면 첫 실행도 빠르게 표시되는 것을 확인했다.

이 현상은 카메라 코어 준비 뒤 미리보기 뷰가 만들어지기 전의 빈 구간에서 발생했고, 실제 `AVCaptureSession` 구성과 `startRunning()` 시간은 그 이후 수백 밀리초 수준이었다. 따라서 디버거가 연결된 새 설치의 단 한 번의 콜드 스타트만으로 카메라 초기화나 SwiftUI 구조를 다시 변경하지 않는다.

실제 시작 성능을 검증할 때는 다음 순서를 사용한다.

1. Scheme의 Run > Info에서 `Debug executable`을 끄고 실제 기기에서 새 설치 첫 실행을 확인한다.
2. 배포 조건은 Release 또는 TestFlight 빌드로 확인한다.
3. 병목 분석이 필요할 때는 Instruments의 App Launch나 Time Profiler를 사용한다.
4. 일반 디버깅이 필요하면 `Debug executable`을 다시 켠다.

현재 공유 Run Scheme은 성능 확인을 위해 디버거 연결을 비활성화한다. 콘솔 로그와 중단점이 필요한 작업에서는 Scheme 설정을 임시로 되돌린다.

참고: [Reducing your app's launch time](https://developer.apple.com/documentation/xcode/reducing-your-app-s-launch-time), [Apple Developer Forums: slow launch under debugger](https://developer.apple.com/forums/thread/800067?answerId=859763022)
